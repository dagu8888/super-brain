# P0 死信修复记录（inbox-triage 纯文本负载）

> 日期：2026-11-08 ｜ 执行：Trae Agent ｜ 用户批示：解决 DSH 备忘录积压死信
> 回滚点：git tag `v2.0-pre-textfix` ｜ 备份：服务器 `/root/backups/v3-textfix-*`、`v3-textfix2-*`

## 现象

DSH 通过 `/cmd submit` 批量提交微信备忘录，全部进入 `inbox-triage` 后变成 `dead`（当日累计 16 条），且 DSH 不知情、持续补发。

## 根因（两层，逐层暴露）

| 层 | 根因 | 证据 |
|---|---|---|
| 第一层 | `handle_inbox_triage` 只认 `payload["path"]`，外部入口提交的是纯文本 `{text}` → KeyError，且被判定为「不可重试」直接 dead | `error: 不可重试: 'path'` |
| 第二层 | 修复落盘后，长文本（10–20K 字符）导致 LLM 输出超 `max_tokens=3000` 被截断 → JSON 不完整 → 解析失败 | `triage_json_failed`，`Unterminated string` |

## 修复内容

1. **兼容纯文本**：无 `path` 有 `text` 时，自动落盘为 `00-Inbox/.staging/inbox-<sha1前10>.md`（走 PathGuard 留痕），复用原有归档、同源幂等、清理逻辑。
2. **落盘位置**：用 `.staging` 子目录，`inbox_adapter` 只扫 `*.md` 不递归 → 避免同一文本被二次入队。
3. **输出容量**：`max_tokens` 3000→8000；prompt 约束正文 ≤3000 字（超长原文按主题合并要点）。
4. **失败语义**：JSON 解析失败改为 `RetryableError`（重试而非直接死信），并记 `triage_json_failed` 便于诊断。
5. **顺带修复**：`add-agent` 新建 worker 默认 `llm: false` 导致接单即死 → 默认改为可用 LLM。

## 已知残留

1. 备忘录分片存在重叠（同一片补传多次），生成了数篇主题相近的知识文件，需后续人工或脚本合并去重。
2. 超过 12K 字符的原文仍只送 LLM 一次（prompt 已要求按主题合并），细节可能被压缩；原文完整保留在 `tasks.payload` 与 `events.payload` 中可追溯。
3. 死信重试仍为 3 次上限，稳定失败仍会 dead——属设计行为。
