> 架构主管：Trae Agent ｜ 2026-11-08 ｜ 状态：**待评审**
> 依据：幕僚长 V2 总指令 + V1 审计报告 ｜ 约束：不引入 Kafka/Redis/PostgreSQL，复用 SQLite(WAL)；单进程多线程起步，预留进程化接口；与 V1 数据兼容。

## 0. 设计决策总览

| 决策 | 结论 | 理由 |
|---|---|---|
| 事件总线 | SQLite `events` 表（不引外部 MQ） | 单服务器、量级小、V1 已有 WAL |
| 任务队列 | `tasks` 表升级版（替代 V1 task_queue，迁移而非删除） | 加租约/fencing/重试/死信 |
| Router | 同进程线程，规则层(filters.yaml)先行，模型层兜底 | 省钱、毫秒级过滤已有设计 |
| Worker | 线程起步，接口按"未来可拆进程"设计 | 总指令允许 |
| 权限 | 代码层 PathGuard + 高危操作确认，YAML 仅作声明 | 审计 R6 |
| 记忆体系 | frontmatter Schema + 文件级检索接口，向量库暂缓 | 量级不足，预留接口 |

## 1. 事件模型（C1）

统一标准事件，所有来源经 Adapter 转换后入 `events` 表：

```json
{
  "event_id": "evt_20261108_ab12cd",     // 唯一 ID（ULID 风格：日期+随机）
  "source": "inbox|cron|watchdog|webhook|user|agent",  // 来源
  "type": "inbox_note|kb_change|heartbeat_lost|manual",// 事件类型
  "payload": {},                          // 原始内容引用
  "priority": 0,                          // 0普通 1高 2紧急(URGENT)
  "dedupe_key": "inbox:00-Inbox/xxx.md",  // 幂等键，UNIQUE 约束
  "parent_id": null,                      // 关联事件（如重试链）
  "status": "new|filtered|routed|done|dead",
  "created_at": 1731030000
}
```

- **幂等**：`dedupe_key` UNIQUE，重复事件 INSERT OR IGNORE，天然防重复派发（验收 4 重复事件）。
- **首批 Adapter（D1 实现）**：InboxAdapter（文件扫描，复用 V1）、CronAdapter（定时事件）、WatchdogAdapter（异常事件）。webhook/email/群聊 Adapter **只留接口不实现**。

## 2. 规则与模型双层判断（C2）

```
event → 规则层(filters.yaml) → DROP(留痕) / URGENT(直派+回执) / ALLOW ↓
                                                              模型层(DeepSeek)
                                                              → 意图分类+Worker选择
                                                              → JSON Schema 校验
                                                              → 权限复核(§5)
                                                              → 入 tasks 表
```

- 规则层：消费 V1 已有 `40-Agents/router/filters.yaml`（DROP/ALLOW/URGENT 三级动作原样实现）。
- 模型层：输出强制 JSON Schema `{intent, worker, subtasks[], reason}`，校验失败→规则层 default 兜底（chat-worker），**模型永远不能指定权限外操作**（§5 复核在入队前执行）。
- 原则：规则能定的绝不调 LLM（V1 filters 设计已覆盖群消息/PR/CI/邮件/库变更五类源）。

## 3. 任务状态机与租约（C2/E1 核心）

```
pending ──原子领取──→ doing ──成功──→ done
   ↑                   │失败(可重试,retry_count<3)→ pending(退避后可见)
   │                   │失败(不可重试/超限)──────→ dead(死信,人工)
   └──租约过期──────────┘(reaper 回收，fencing 校验后重置)
        cancelled(用户取消,终态)
```

**tasks 表（v2，由 task_queue 迁移）：**

```sql
CREATE TABLE tasks(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  event_id TEXT,                     -- 来源事件
  type TEXT NOT NULL,                -- inbox-triage|chat|code|research
  payload TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending',  -- pending|doing|done|failed|dead|cancelled
  priority INTEGER DEFAULT 0,
  retry_count INTEGER DEFAULT 0,
  max_retries INTEGER DEFAULT 3,
  not_before INTEGER,                -- 退避：指数 2^n * 30s
  lease_owner TEXT,                  -- 租约持有者(worker名)
  lease_token INTEGER,               -- fencing token，每次领取+1
  lease_expires_at INTEGER,          -- 租约到期(默认领取+120s)
  created_at INTEGER, claimed_at INTEGER, done_at INTEGER,
  result TEXT, error TEXT,
  UNIQUE(type, payload)              -- 沿用 V1 幂等
);
```

**原子领取（单事务条件更新，防双领）：**

```sql
UPDATE tasks SET status='doing', lease_owner=?, lease_token=lease_token+1,
  lease_expires_at=?, claimed_at=?
WHERE id=(SELECT id FROM tasks WHERE status='pending' AND type IN (...)
          AND (not_before IS NULL OR not_before<=?) ORDER BY priority DESC, id LIMIT 1)
  AND status='pending'
RETURNING id, lease_token, payload;   -- SQLite 3.35+ 支持 RETURNING（Ubuntu24 自带 3.45 ✓）
```

- **提交结果带 fencing**：`UPDATE ... WHERE id=? AND lease_token=?`，token 不匹配=旧 Worker，拒绝提交（验收 3 核心）。
- **续租**：执行中每 30s `UPDATE lease_expires_at WHERE id AND lease_token`。
- **回收（reaper）**：watchdog 每轮 `UPDATE tasks SET status='pending', lease_owner=NULL WHERE status='doing' AND lease_expires_at<now`，回收时 lease_token 不变（旧 Worker 提交会被拒）。
- **重试**：可重试错误（网络/LLM 5xx/DB 锁）→ pending + `not_before=now+2^retry*30s`；不可重试（Schema 校验失败/权限拒绝）→ 直接 dead。
- **取消**：`UPDATE status='cancelled' WHERE id AND status IN ('pending','doing')`，Worker 每轮检查自身任务状态发现 cancelled 即停。

## 4. Router / Worker 接口（C3）

**Router 线程（D3）**：事件循环 = 拉 new 事件 → 规则层 → (必要时)模型层 → 入 tasks → 即返回。**Router 从不等待 Worker**（对话/后台解耦的结构性保证：根本没有"等待"这个调用存在）。

**Worker 接口（所有 Worker 实现同一契约，未来可拆进程）：**

```python
class Worker:
    name: str; task_types: list[str]; permissions: dict  # §5
    def handle(self, task, ctx) -> TaskResult: ...
    # ctx: TaskContext{db(受限), repo_path, llm(按需), emit_event, report_progress}
```

**首批 Worker 与处理器（D4）：**

| Worker | 任务类型 | 处理器 | 状态 |
|---|---|---|---|
| knowledge-worker | inbox-triage, kb-organize | 复用 V1 handle_inbox + frontmatter 注入(F1) | 迁移 |
| chat-worker | chat-query | 查知识库→LLM 生成答复→写 60-Outputs | 新实现 |
| code-worker | code-review, ci-analysis | 拉 diff→LLM 评审→写 60-Outputs | 新实现 |
| research-worker | research | 搜索→整理→报告写 60-Outputs | 新实现 |

**进度查询/取消**：`task_status(id)` 只读查询接口；事件留痕含 progress 事件，Router 汇总回复时读取。

**会话状态（C2/持久化）**：`sessions(thread_id PK, worker, state_json, updated_at)`——实现 V1 router.yaml 里声明但缺失的 routing_table。

**Supervisor（E3）**：主线程每 30s 检查各 Worker 线程 `is_alive()` + 心跳新鲜度，死了重建线程并记事件 `worker_restarted`。

## 5. 权限模型（C5/E5）

```python
PERMISSIONS = {
  "knowledge-worker": {"write": ["00-Inbox/","10-Knowledge/","30-Reviews/"], "exec": False, "llm": True},
  "chat-worker":      {"write": ["00-Inbox/","60-Outputs/"], "exec": False, "llm": True},
  "code-worker":      {"write": ["60-Outputs/","50-Events/"], "exec": False, "llm": True},
  "research-worker":  {"write": ["60-Outputs/"], "exec": False, "llm": True},
}
# 全员只读默认 **；40-Agents/ 90-System/ 70-Assets 外密钥文件 全员禁写
```

- **PathGuard**：所有文件写操作经 `guard.write(path)`，解析为绝对路径后校验 allowlist + denylist（`llm.json`、`*.key`、`.git/` 硬禁），越权→抛 PermissionDenied + 写 `perm_denied` 审计事件（验收 6）。
- **高危确认**：`exec` 类操作（shell）全员 False，需要时走人工确认事件，无自动通道。
- 模型层输出在入队前过一次权限复核：Worker 目标目录 ∉ allowlist → 拒绝并降级为 chat-worker 记录。

## 7. Watchdog v2 接口（E4）

watchdog.sh 保留 git/inbox 检查；新增 `90-System/runtime/health.py`（只读 DB+系统指标，cron 每 10min）：

| 检查 | 阈值 | 动作分级 |
|---|---|---|
| Worker 心跳 | >15min | B 级：Supervisor 重启线程，连续 3 次失败→C 级告警 |
| 卡 doing/租约过期 | 存在即回收 | A 级：自动回收（fencing 保护） |
| 队列积压 | pending>20 或最老>30min | C 级：告警事件 |
| LLM 可用性 | 连续 2 次调用失败 | C 级：告警 + inbox-triage 暂停入队 |
| 磁盘/内存 | 盘>85% / 可用内存<150MB | C 级：告警 |
| 死信 | dead>0 | C 级：告警需人工 |

## 11. 修订 R1：TRAE 双角色接入 + Agent Registry（2026-11-08 补充指令，并入主方案）

### 11.1 身份模型（身份与角色强制分离）

系统内只有两类逻辑身份，**指挥权与执行权互不继承**：

| 身份类型 | 实例（全局唯一 agent_id） | 权限 |
|---|---|---|
| chief（指挥入口） | grok-chief, deepseek-chief, maus-chief, dsh-chief, **trae-chief** | 下达任务、查询任务中心、查询进度、发起协作/转交、关联指令到已有任务、接收 Router 汇总 |
| worker（执行角色） | knowledge/chat/code/research-worker, **trae-developer** | 按注册能力领取执行任务，无指挥权 |

- trae-chief ≠ trae-developer：两者独立注册、独立权限、独立心跳，**不因同出 TRAE 而共享任何权限**。
- trae-developer 注册能力：code-dev / arch-review / tech-doc / code-test（以实际验证为准）。

### 11.2 Agent Registry（动态能力注册，DB 新表）

```sql
CREATE TABLE agents(
  agent_id TEXT PRIMARY KEY,        -- 全局唯一
  kind TEXT NOT NULL,               -- chief|worker
  capabilities TEXT NOT NULL,       -- JSON数组，如["code-dev","code-test"]
  task_types TEXT,                  -- worker可领取的任务类型（chief为NULL）
  permissions TEXT NOT NULL,        -- JSON，PathGuard规则引用
  verified INTEGER DEFAULT 0,       -- 0未验证 1已验证（验证方式：注册后跑通一个探针任务）
  status TEXT DEFAULT 'active',     -- active|suspended
  registered_at INTEGER, last_seen INTEGER
);
```

- **派发铁律：只按 `capabilities + verified=1` 派单，禁止按名称推断**。未验证 Agent 只能领 probe 任务。
- 注册即落库；`last_seen` 由心跳维护，Supervisor 以此判活。

### 11.3 统一任务中心与 canonical_user_id

```sql
CREATE TABLE user_identities(
  source TEXT NOT NULL,             -- grok|deepseek|maus|dsh|trae
  source_user TEXT NOT NULL,        -- 该入口看到的用户标识
  canonical_user_id TEXT NOT NULL,  -- 统一用户ID（大古老师=dagu8888）
  PRIMARY KEY(source, source_user)
);
```

- 所有事件/任务带 `canonical_user_id`；五入口共享同一 `tasks`/`events` 表 = 统一任务中心，天然满足"任意入口查任意任务"。
- chief 指令接口（D3 Router 实现）：`submit / status(id) / list(filter) / progress(id) / delegate(id,to) / link(instruction,task_id) / cancel(id)`。

### 11.4 验收追加（并入总指令验收清单第 9 条）

五入口（grok/deepseek/maus/dsh/trae）各提交一个测试任务，验证：
- 均解析到同一 canonical_user_id；
- 均能读写统一任务中心，且能查到其他入口发起的任务；
- trae-chief 发起的任务正常经规则层→Router→Worker；
- trae-developer 以独立身份领取并通过 fencing 提交结果；
- 用 trae-chief 的凭据尝试领取执行任务 → **拒绝并记 perm_audit**（反之亦然）。

### 11.5 影响评估

- DB：+2 表（agents、user_identities），tasks/events 各 +1 列（canonical_user_id），迁移脚本同步更新。
- Router：chief 指令接口是 Router 的自然延伸，不新增组件。
- V1 资产：heartbeats 保留，agents 表与其并存（V2 内逐步以 agents.last_seen 为准）。
