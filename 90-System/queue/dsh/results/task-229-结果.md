## 二、从执行方（主机侧节点）看，Super-Brain V2.0 最该先补的 3 个缺口

> 与 Trae 回执（派单目标校验 / 中台拆解 / 结果回传）不重复——以下三条全部来自本次接入的**实测现场**。

1. **节点侧没有现成信使，"长连接节点"只能自造**：仓库里的 `messenger.py` 是**服务器侧**程序（直连 `90-System/runtime/state.db`）。主机节点（无该 DB、无 chief 口令）拿不到任何现成客户端：本次 #229 在 DB 里 `pending` 已 9 小时，服务器 `queue/dsh/` 却是空目录——任务没落到交接面上。我按规约自造 `tools/duty-room/dsh1-courier.py`（SSE 长连 + 只读 API 拉取 + 幂等落 `queue/dsh/`）才闭环。**建议**：把"节点客户端信使"提升为正式组件（与服务器 messenger 同包、按实例名参数化），任何新节点接入零自造。
2. **凭据分发是接入的唯一硬断点，且没有自助通道**：chief 口令全靠古大人肉私发；本次古大给的 GitHub PAT 在 `/cmd` 实测 `401 {"ok":false,"error":"无效口令"}`——凭据类型搞混、节点就整段瘫痪（写类指令全不可用）。**建议**：① 口令与仓库 PAT 分开发放并注明用途；② 增加"口令自检"入口（如 `GET /whoami` 只回身份不回权限），节点上线前自证；③ 口令轮换与吊销走 /cmd 指令化，不靠改 api_tokens.json + 重启。
3. **任务账本与交接面双源不一致，取消不回收**：`tasks` 表（DB）与 `queue/<节点>/`（文件）没有强一致保证——Trae 已报"取消后队列文件残留"，本次反向又见"DB 有 pending、队列无文件"。**建议**：给队列文件加任务状态戳（信使每轮对账），或让节点只认 DB 状态、队列文件纯投递；并补一个"孤儿任务/孤儿文件"对账器（可由我实现，见 A 类）。
