## T9-1 认领超时进 D2

**实现**（`runtime.py`，随 reaper 现有 60 秒节拍顺带做，不新增线程、不新增 LLM 调用）：

- 判定口径：`status='pending'` 且 `claimed_at IS NULL` 且 `created_at` 早于 `now-600`，且 payload 点名了具体执行方（`to` / `to_agent`），且未带 `no_claim_timeout`。
- 链路：① 告警发起 chief（落成 priority=2 的 assist 任务，信使写进该幕僚长队列，与既有告警同一姿势）→ ② 名册中有在线兄弟实例则改派一次并重置计时 → ③ 无候选或改派后再超时 → 状态置 `dead` + 再次告警。
- 阈值：`CLAIM_TIMEOUT = 600` 秒；兄弟实例"在线"沿用 5 分钟心跳阈值（`OFFLINE_GRACE = 300`）。
- 豁免标记：`payload.no_claim_timeout = true`，默认不豁免。
- 不误杀保障：只处理 `claimed_at IS NULL`，已被领取过又被 reaper 退回 pending 的任务不受影响；未点名的 worker 池任务不属该场景。
- 并发安全：告警前做原子占位（`json_extract(..._claim_timeout.alerted_at) IS NULL` 条件更新），多进程同时扫到也只告警一次。

**最终口径（供 Muse 复测对齐）**

| 项 | 口径 |
|---|---|
| 超时阈值 | 600 秒，从 `created_at` 起算；改派后 `created_at` 重置为新时刻 |
| 豁免 | payload 中 `no_claim_timeout: true` |
| 改派候选 | 名册 `kind='instance'` 且 `status='active'`、排除原目标、其幕僚长心跳在 300 秒内 |
| 改派次数 | 最多 1 次 |
| 终局 | 死信（`status='dead'`）+ 两次告警（首次超时、转死信各一次） |
| 巡检频率 | 60 秒（reaper 线程内，无额外线程） |

**生产验证**（18:50，真实生产库）：
- 插入回拨 700 秒的测试任务 #286（点名 DSH二号@笔记本）→ 扫描后：产生告警任务 #287「【认领超时告警】任务 #286 点名「dsh2-chief」已 11 分钟无人认领」，无在线兄弟实例 → #286 转 `dead`，产生告警 #288「【死信告警】…已转死信」
- 改派路径（有在线兄弟）在回归测试中验证：`T9-1-4` 改派保持 pending 并指向 Trae@笔记本，`T9-1-5` 再次超时转死信

**自动扫描复测**（部署后，不手工触发）：插入回拨 700 秒的测试任务 #289 → 70 秒内 reaper 自动扫到 → 产生 #294「【认领超时告警】任务 #289 点名「DSH二号@笔记本」…」→ 无在线兄弟实例 → #289 转 `dead`（错误信息「认领超时：600 秒无人认领且无在线兄弟实例」）→ 产生 #295「【死信告警】…」。扫描链路不依赖人工触发，已实证。

**如实上报的两点**：
1. **改派分支在生产环境实际不会命中**：兄弟实例"在线"判定依赖幕僚长心跳，但幕僚长是外部 API 调用方、从不写 heartbeats，因此 `_online_sibling` 当前恒返回空，生产上等价于「无候选 → 直接死信」。要真正启用改派，需把在线判定改成「该实例名下近期有任务认领/上报」或「最近一次 API 调用时间」。此改动超出本包授权口径，**请裁定是否开下一单**。
2. 告警里点名为 `dsh2-chief`（agent_ref）而非「DSH二号@笔记本」，已修正为优先显示实例名，随本次部署生效。

**上线前处置**：任务 #273、#277、#282、#283 均为「等指定 Agent 上线再做」类（其中 #277/#282/#283 是 DSH 接入验收），已按规约打 `no_claim_timeout` 豁免，避免上线瞬间被误杀。

## T9-2 取消计划队列文件清理 + 取件验状态规约

**实现**（`messenger.py` 新增 `_cleanup_cancelled`，随信使 10 秒节拍）：扫描各节点队列的 `task-*.md`，任务状态为 `cancelled` 的**移入该队列 `done/`**（不删除）。选 `done/` 的原因：与现有收口锚点一致，且 `done/` 同名文件同时是写手的幂等依据，取消文件挪走后不会被二次写出。

**生产证据**：部署后自动归档生效——`queue/dsh/done/` 增至 4 个文件、`queue/dsh2/done/` 增至 2 个，此前残留的已取消任务文件 #253、#257、#259 均已从待办区消失。另以测试任务 #289 复测：置 `cancelled` 后 15 秒内，其队列文件 `task-289-*.md` 自动挪入 `queue/dsh2/done/`，已在待办区消失。

**规约**：`90-System/queue/README.md` 节点规约新增第 2 条——「执行前先经网关验一次任务状态，`cancelled` 的不执行、直接写说明到 results/ 回报」，并注明信使会自动归档取消文件。该段落可被 `kb_search` 命中（关键词「cancelled」）。

## T9-3 运维观察（只诊断，未改配置）

- 服务侧无崩溃：`systemctl show -p NRestarts` = **0**；17:00 后 `journalctl` 无 `Traceback` / `error` 记录；当前进程 17 个线程，`ulimit -n` = 65535，均远未触顶。
- 但运行日志里今日有 **5 次** `thread_crashed: router, database is locked`（07:12、08:41、09:03、09:08、18:49），均为部署重启瞬间并发写库导致，supervisor 已自动拉起，未造成任务丢失。
- `RemoteDisconnected` 的成因判断：网关 `BaseHTTPRequestHandler` 未设置 `protocol_version`，默认 HTTP/1.0 且响应后主动断连，客户端复用 keep-alive 连接时就会收到 RemoteDisconnected——**属客户端感知，不是服务异常**，重试即通符合该特征。
- 结论：当晚服务无异常。建议（不改，等裁定）：① 网关改 HTTP/1.1 + 连接复用；② `db()` 的 10 秒 busy_timeout 视情况提高。
