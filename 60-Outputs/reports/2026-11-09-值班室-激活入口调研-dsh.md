## 二、值班程序推荐方案（按红线对齐排序）

> 包内红线：值班程序是脚本、**永不调用 LLM、永不高频轮询、不开任何入站端口**、断线自愈、只响应名册内点名任务。

- **B 档 · 主力推荐：SDK stdio JSON-RPC 常驻**
  值班程序（Python，仅标准库）启动时 spawn `dsh --profile sdk` 子进程，握手 initialize 后保持常驻；SSE 队列变更到达 → `session/prompt` 注入值班会话 → 流式收事件 → `session/wait` 收口 → 结果回写。
  **对齐性：outbound stdio 子进程，零入站端口；值班程序自身零 LLM；长连不轮询；进程级断线自愈（子进程死了 respawn）。**
- **A 档 · 零代码兜底：任务计划程序 + headless**
  `dsh --profile headless --session-id <值班会话id> "<任务>"`，stdout 收答案、诊断走 stderr。任务计划程序触发（开机自启/事件触发），一次性进程，无常驻内存。适合作为 B 档的降级开关与联调首验。
- **C 档 · 暂缓：duty-bridge 插件（loopback HTTP）**
  能做到"一行 HTTP 投递"，但要开本地监听端口——**与"不开任何入站端口"红线冲突**。除非幕僚长特批，不推荐本期实施。

## 三、风险与对策

| 风险 | 证据 | 对策 |
|---|---|---|
| 同一 sessionId writer 独占，并发占用被拒 | recon 报告 §风险① | 值班会话专用 id + 内部串行队列，绝不与 GUI 会话共用 |
| SDK stdout 是协议帧，混日志即坏 | recon §风险② | 值班程序对子进程 stdout 只做协议解析；日志只写文件，绝不进 stdio |
| 插件与 harness 版本耦合 | 实测 dsh-ide-git@0.22.0 因 engines.dsh>=0.2.2-alpha.2 被 0.2.1-rc.5 跳过 | 锁定版本；harness 升级前跑值班室回归 |
| headless 一次性无跨任务记忆 | 模式本身 | 用 `--session-id` 续接同一持久会话保持上下文 |
| 实跑未验证（避免烧额度） | 本次全部 --help 级验证 | 留联调清单：口令交付后 A 档 5 分钟首验 → B 档 30 分钟常驻验证 → 空转 24h 稳定性 |
