## 1. 服务器上现在实际在跑什么

**进程与启动方式（实测）**：

| 项 | 实况 |
|---|---|
| 唯一业务进程 | `/usr/bin/python3 /root/super-brain/90-System/runtime/runtime.py`（pid 27492，单进程多线程） |
| 托管方式 | systemd 单元 `super-brain.service`（`Restart=always`，`WorkingDirectory=/root/super-brain`），单元文件在 `90-System/runtime/super-brain.service` 有副本 |
| 网关 | 不是独立进程：`runtime.py` 主线程启动时调用 `api_server.maybe_start()`，在同一进程内起 HTTP 服务，监听 `0.0.0.0:18765` |
| /cmd 实现位置 | `90-System/runtime/api_server.py` 的 `do_POST`（鉴权：Bearer 口令→幕僚长身份）→ 调 `runtime.py` 的 `chief_execute()` |
| 只读控制台接口 | 同进程内 `console_api.py`（/api/* GET，viewer 只读口令） |
| 任务数据存储 | SQLite：`/root/super-brain/90-System/runtime/state.db`（WAL 模式，实测 6.8MB），核心表 `events / tasks / agents / sessions / heartbeats / user_identities / perm_audit` |
| 文件留痕 | `50-Events/runtime-YYYY-MM-DD.jsonl`（审计日志，追加写） |
| 配置（不入库） | `api_tokens.json`（600 权限，幕僚长口令）、`llm.json`（600 权限，模型层密钥） |

## 2. 现有任务流转的真实路径（submit → done）

1. 幕僚长 `POST /cmd {"cmd":"submit",...}` → `api_server.do_POST` 鉴权（口令比对出身份）
2. → `runtime.chief_execute()` 校验 chief 身份 → `emit_event()` 写 `events` 表（status='new'；此处已有：幂等去重、跳数熔断、指令数据分离）
3. → `router_loop` 线程轮询捞 `status='new'` 事件 → 规则层（`40-Agents/router/filters.yaml`）→ 不中则模型层（LLM 意图分类，输出校验+越权降级）
4. → `enqueue_task()` 写 `tasks` 表（status='pending'）
5. → `worker_loop` 线程 `claim_task()` 租约认领（fencing token，按类型+优先级）
6. → `run_handler()` 执行 → 结果写 `tasks.result/error`，状态 `done/failed/dead`
7. 全程状态只存 `state.db`；进度事件 `task_progress` 写 `events` 表

一句话：**事件进 events 表，任务进 tasks 表，状态全在 SQLite，文件系统只留审计日志和产出物。**

## 3. 中台（Orchestrator）落点评估

**建议挂点：`emit_event()` 之后、`router_loop` 派工之前。**

即新增一个 `orchestrator_loop` 线程，订阅 type 为 `orchestrate`（或带拆解标记的 manual）的事件：负责把大任务拆成子任务（多条 tasks，互相关联 parent）、分配目标、在各子任务 done 后汇总收口写回。选这里的理由：

- 入口侧的 `chief_execute` 七接口一个都不用动，8 个幕僚长的接入协议零变化
- 拆解产物直接走现有 `enqueue_task`，worker 认领、租约、熔断、复盘视图全部白嫖
- 汇总结果可复用 `assist/report` 协作池或写 60-Outputs，无需新存储

**需要动的文件**：仅 `90-System/runtime/runtime.py`（加一个线程+两个函数）与 `migrate_v2.py`（如需新表）；可能加一行 `filters.yaml` 规则。

**绝对不能动的**：
- `api_server.py` 的 `/cmd` 鉴权与请求格式（8 个幕僚长按此接入，口令即身份）
- `chief_execute` 的七接口语义（submit/status/list/progress/delegate/link/cancel）
- `agents` 表现有 chief 行与 `api_tokens.json`
- `state.db` 表现有列（只许 `CREATE TABLE IF NOT EXISTS` 新表，不许 ALTER 老表）

## 4. 实例名册现状

**现在只认笼统名字，不认实例。** 网关唯一的名册是 `agents` 表：`agent_id` 如 `grok-chief`、`chat-worker` 这类角色名；`delegate` 只校验「是不是已验证激活的 worker」，`submit` 则完全没有目标名校验。`DSH一号@主机`、`DSH二号@笔记本`、`Trae@笔记本` 这类「哪个 AI 跑在哪台机器上」的实例概念，目前**不存在于任何表**——这正是 T3 要补的：新建 `registry` 实例名册 + 网关校验（随本批交付）。
