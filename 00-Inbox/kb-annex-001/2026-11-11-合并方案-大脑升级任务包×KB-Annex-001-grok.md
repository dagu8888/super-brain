# 合并方案（一页纸）

**目标**：把 Super-Brain 的知识库从「能存能写」升级到「会整理、查得准、不过期」，并补齐运行时几处被事故标过价的缺口。一句话验收：**新 Agent 只靠读库就能分清哪条现行、哪条已失效，检索质量有一份可复测的分数。**

**合并原则**：两包只做**一次**自审计（G-KB0）；15:36 包的 P1/P2/P3 与 KB-Annex 的 U1–U6 按下表对齐，取两者中更严的验收口径；红线取并集。

**风险**

1. 检索改造影响生产：P2 新索引只能影子跑，不改 `kb_search` 现行代码；切换要大古批准。
2. 评测被污染：kb_search 扫全目录，本目录里的金标答案、对账表会被搜到。已把金标题目和答案存成 `.tsv`（kb_search 不扫这个扩展名）；后续每次回放都要排除 `00-Inbox/kb-annex-001/`。
3. 服务器负载：未命中一次约 40 秒满核；基线已按单线程、每次间隔 3 秒执行，后续回放保持低频。
4. 凭据暴露：库里已有明文凭据（见对账表第四节）。处置会碰凭据和 Git 历史，必须大古决定。
5. 自验风险：grok-chief 在 `projects.EDITORS` 里，可以给自己的阶段验收；本方案约定所有阶段由 Muse 初审、大古终审，施工方不调用 `phase_accept`。

**需要大古拍板的事**（详见分歧清单）

1. 批准 U1 规范与映射表后，是否按映射表小步迁移？先迁哪一批（建议：先标测试残留和重复页的状态，不搬文件）。
2. 编译层是否单列第五类「方法页」（SOP/技能），还是并入概念页。
3. 个人备忘（11 篇）是否单开私密命名空间、是否继续让 kb_search 搜到。
4. 明文凭据处置：轮换服务器登录口令、从 Git 历史清除、文件改为口令包引用，由谁来做、何时做。
5. 心跳丢失告警每小时写一篇回写（已 150 篇）：是否停止写入知识库或改到运行日志（涉及 runtime，属生产变更）。
6. P2 是否立项：向量模型、索引存放位置、是否新增进程或依赖（可能涉及花钱和新服务）。
7. 冲突处理路线：建议「双时态失效」Markdown 原生版（`valid_to` + `superseded_by`，不删旧页）；备选「只加不改」。

**红线（并集）**：Markdown/Git 唯一真源，索引可重建；state.db 是唯一任务台账，不建第二台账；不动 40-Agents / 90-System；不删、不搬、不改名存量页（批准前）；凭据零接触；不高频轮询；花钱先报批；DB 变更要有迁移和回滚；完成声明不等于验收。
