# U2 查询 SOP v1

> 「争议」= 待批准。适用于所有经网关 `kb_search` / `kb_read` 查库的 Agent。不改任何代码，只规定查法。

## 三步查法

1. **先读索引定位**：`kb_read` 读 `00-Inbox/kb-annex-001/2026-11-11-U2-总索引-grok.md`（批准迁移后路径会变，以映射表为准）。
   - 先看「编译层」四组（决策 / 实体 / 概念 / 综合），再看系统规范；状态是「部分失效 / 已失效? / 争议」的，答题时必须说明。
   - 索引超过 8000 字一次读不完时，用 `max_chars` 分段读，或先 `kb_search` 索引里的标题关键词。
2. **再读目标页**：`kb_read` 读索引定位到的页面，答案引用「页面路径 + 小节」。
3. **不够再下钻原料层**：编译层没写的，才去 `60-Outputs/`、`00-Inbox/` 找原始回执和结果；原料层内容引用时注明「原料，未经编译」。

## kb_search 用法（现行版本的限制，见 G-KB0）

- 参数名只能是 `q` / `text` / `keyword`；客户端超时至少设 90 秒。
- 它是**字面子串**查找，整句问题几乎查不到：先拆成 2-6 字的**短关键词**，一次一个。
- 结果不排序、最多 20 条，前面常被 `90-System/queue/`、`50-Events/` 等非真源文件占满；只认 Git 跟踪的路径，忽略 `90-System/queue/` 下的命中。
- 未命中也要约 40 秒，**不要循环高频调用**；同一问题最多 3 个关键词。

## 答题纪律

- 没有找到 = 回答「知识库里没有」，不要拿模型常识补。
- 找到多个说法不一致：按页面 `status` / `valid_to` / 提交时间说明哪条现行、哪条已失效；判断不了就标「争议」上报，不要自己抹平。
- 命中含凭据的页面：不得复述凭据内容，只说「该页含敏感信息，已上报」。

## 验收口径（照 KB-Annex U2）

- 索引覆盖率：331 / 331（100%）。
- 「抽 20 个真实问题，按 SOP 定位正确页面 ≥90%」：由 Muse 独立抽题、独立执行，施工方不自验。可直接用 U3 金标集里的非拒答题当题源。
